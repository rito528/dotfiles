# create-issue スキル

issue 本文は、その時点の合意を表す長寿命な文書である。AI が生成する調査結果や実装案は未検証の主張であり、コードが変わると古くなるため本文に残さない。実装開始時には issue-agreement スキルが issue を現在のコードと照合し、必要な調査を作り直す。このスキルの役割は、人間が決めた要求・意図・制約・未決定事項を、意味を増やさず issue に残すことである。

## 原則

issue 作成 agent は、要求を完成させる役割ではない。入力にない要求・制約・設計判断を補完して、issue を完全に見せてはならない。不足している情報は不足したまま保持し、人間の判断が必要なら未決定事項として示す。

issue 作成 agent は、原因や実装方法を特定する役割でもない。issue を詳しく見せるためのコード調査はしない(範囲は後述)。

短くすること自体も目的ではない。目的は、人間が決めた意味だけを、人間が全文を読んで合意できる形で残すことである。要約によって、異なる要求や条件を一つに潰して意味を変えてはならない。

このスキル全体を通して、次の 3 つをすべて避ける。

```text
AI が勝手に要求を補完する
→ 禁止

AI が実装上の判断を要求として issue に書く
→ 禁止

AI が実装上の細かい判断を全部ユーザーへ質問する
→ 禁止
```

## 入力の出所と、ユーザーが採用したかを分ける

ユーザーが会話に入力したものすべてが、ユーザーの要求や決定ではない。貼り付けられた文章、他の AI agent の出力、既存 issue、設計メモ、調査結果、第三者の意見、レビューコメントは、ユーザーが運んできた素材であって、ユーザーの判断そのものではない。

- **出所**(誰が書いたか)と、**採用**(ユーザーがそれを要求・制約・スコープとして引き受けたか)を別の軸として扱う。
- ユーザー自身が要求・制約・スコープとして採用したことが明確な内容だけを、「ユーザーの要求」「ユーザーの決定」に分類する。
- 貼り付けられた素材の中の記述は、素材の中での性質で分類する。他の agent の推測は、ユーザーが貼り付けても推測のままである。

これは次の連鎖を断つためである。

```text
別の AI agent が推測する
→ ユーザーがその文章を貼る
→ create-issue agent がユーザー入力として扱う
→ 推測がユーザー要求へ変換される
→ issue に確定事項として残る
```

AI の推測は、agent や会話を何回経由しても人間の決定にならない。ユーザーが採用したかどうか判断できない記述は、確認できる場面では確認し、できない場面では推測・仮説として扱う。

## 記述の分類

本文に採用する前に、候補となる各記述を次のいずれかに分類する。分類ラベルを本文に表示する必要はないが、分類せずに採用してはならない。

| 分類 | 例 | 扱い |
|---|---|---|
| ユーザーの要求 | 「CSV でも取り込めるようにしたい」 | 本文に書く |
| ユーザーの決定 | 「既存の UI は変えない」「同期処理は対象外」 | 本文に書く(制約・やらないこと) |
| 合意された仮定 | 「外部 API の通知は少なくとも一度配送されるものとして扱う」 | 仮定と分かる表現で本文に書く(条件は後述) |
| 長寿命な確認済みの事実 | 「外部 API の仕様上、日時は UTC で返る」 | 本文に書く(制約。範囲は後述) |
| 観測の記録 | 「この操作をしたとき 500 が返った」 | 本文に書く(問題) |
| 未決定事項 | 「重複行をエラーにするか上書きするかは未定」 | 未決定事項に書く(範囲は後述) |
| 推論・仮説 | 「原因はおそらくバリデーション漏れ」 | 本文に昇格させない |

推論・仮説は、agent 自身のものでも、貼り付けられた素材由来のものでも、原則として issue 本文に入れない。文章を完成させるために、推論を要求や制約の形に変換することは、最もやってはならない操作である。

推論から未決定事項を作れるのは、その回答によって要求・制約・スコープ・外部から見える振る舞いが変わる場合だけとする。その場合も、仮説の内容を主張せず、問いの形にして未決定事項へ変換する。それ以外の推論は破棄する。

## 仮説と合意された仮定

「誰が言ったか」と「事実として確認できているか」を分ける。人間が「たぶん X が原因」と言っても、それは仮説である。人間由来であっても、コードの構造・原因・実装方法についての未検証な記述は仮説として扱い、そのままでは本文に書かない。人間が「この前提で進める」と同意しても、仮説が事実へ昇格するわけではない。「原因は X である」のように事実の形へ書き換えることはしない。

**合意された仮定**として本文に残せるのは、次のすべてを満たす前提だけとする。

- 未検証であることをユーザーが理解している
- ユーザーが明示的に採用している
- 要求・制約・スコープ・外部との契約のいずれかに影響する
- 原因分析や実装上の作業仮説ではない

残せる例:

- 「外部 API の通知は少なくとも一度配送されるものとして扱う」
- 「既存データは移行対象外とする前提で進める」

残せない例(人間が同意していても本文に書かず、実装時の調査に委ねる):

- 「Redis の競合が原因という前提で直す」
- 「この Service が原因という前提で調査する」

合意された仮定は、仮定であることが本文から分かる表現で書く(例: 「〜という前提を採用する。前提が崩れた場合はこの issue を見直す」)。issue-agreement が合意メモで扱う「仮定」(出典なしで進めることにユーザーが同意した項目)と同じ位置づけであり、そのまま引き継がれる。

## 観測の記録の範囲

観測の記録は、「現在も真かどうか」ではなく「その時点でその現象を観測した」という事実として issue に残す。修正後に再現しなくなっても、issue が生まれた問題の記録として意味を持つ。

書き分けるのは、コードの現在状態を説明する情報と、問題発生時の観測記録である。

- 書かない: 「foo.rs のこの実装が原因で 500 になる」(コードの現在状態に依存する説明)
- 書く: 「ログイン後にプロフィール画面を開くと 500 が返る」(問題発生時の観測記録)

実際に発生・確認した現象、再現手順、期待する挙動、実際に観測した挙動、分かっている範囲の発生条件や環境は、観測の記録として本文に残す。完全な情報は要求しない。

- 分かっている範囲で再現条件や観測結果を書く
- 環境や日時など不明な情報は、不明なままにする
- agent が不足した環境・日時・条件を推測で補完しない

## 長寿命な確認済みの事実の範囲

「確認済みの事実」として本文に書けるのは、次のすべてを満たすものとする。

- issue の要求・制約・スコープを理解するために必要である
- 現在のコード実装に依存していない
- 根拠を確認できる

ここでの「長寿命」は「永遠に真」という意味ではない。外部 API の仕様も将来変わり得るが、issue 作成時点で要求・制約を理解する根拠になるなら残してよい。除外したいのは、コードが変わると古くなる、現在の実装に依存した情報だけである。

残せる例:

- 外部 API や外部システムとの契約
- 要求判断の前提になる外部仕様
- コード実装から独立したドメイン上の制約

実際に観測した現象は、この分類ではなく「観測の記録」として扱う。外部仕様やドメイン上の事実と、観測した現象を同じ分類に混ぜない。

「現在 FooService がこの処理を担当している」「現在このファイルにこの実装がある」のような現在のコード実装に関する事実は、コードを読んで確認できていても本文に書かない。コードの現状は issue-agreement が実装開始時に確認し直す。

## 未決定事項の範囲

未決定事項は無理に解消するものではなく、未決定であること自体を issue に保存してよい情報である。issue 作成の時点で解消するためだけに、ユーザーへ追加質問をしない。

未決定事項に書くのは、要求・制約・スコープ・外部から見える振る舞いについて、人間の判断が必要なものに限る。未決定事項は agent の疑問の置き場ではなく、人間に判断を求める項目の一覧である。

未決定事項にしてよい例(回答によって要求・制約・スコープ・外部から見える振る舞いが変わる):

- 重複データをエラーにするか上書きするか
- 管理者にも同じ操作を許可するか
- 既存データを移行対象に含めるか
- 外部公開 API の互換性を維持する必要があるか

ユーザーへ質問せず、実装時の設計判断として後段へ委ねる例:

- DB のカラム名
- Repository のメソッド名
- どのファイルを変更するか
- 内部 API の構造
- 関数の分割方法
- テストファイルの配置
- そのほか、実装者がコードを読んで妥当に判断できる内部設計

目指す分担は次のとおり。

```text
要求・制約・スコープ・外部から見える振る舞いに関する本当の未決定
    ↓
ユーザーに確認する / issue の未決定事項に残す

実装上の技術的選択
    ↓
issue には残さない
    ↓
issue-agreement 以降でコードを読んで判断する
```

## 不採用案を残す条件

不採用にした方式を issue に残すのは、次のどちらかを満たす場合だけとする。

- 人間が「今後もこの issue の要求・制約として除外する」と決めたもの
- 再検討すると要求そのものが変わってしまう決定

単なる設計比較の結果や、現在のコード事情という一時的な理由で不採用になった方式は残さない。

## issue 作成のための調査を増やさない

「調査した結果を issue に書かない」だけでなく、issue 作成のためだけの調査をそもそも行わない。create-issue は、原因を特定する、実装方法を決める、変更ファイルを探す、コード構造を分析するためのスキルではない。

調査してよいのは、問題の再現条件を確かめる場合と、ユーザーの要求が何を指しているかを確認する場合に限り、その目的に必要な最小限にとどめる。技術的な現状確認、原因分析、実装方針の検討は、実装開始時の issue-agreement に委ねる。

## issue の構成

次の 5 項目で構成し、該当がない項目は省く。

- **問題**: 何に困っているか。バグなら再現手順、期待する挙動、実際に観測した挙動
- **実現したいこと**: この issue が閉じたときに何ができているか
- **要求・制約・前提**: ユーザーの決定、長寿命な確認済みの事実、仮定と分かる表現で書いた合意された仮定
- **やらないこと**: スコープ外と決めた範囲。条件を満たす不採用の決定もここに書く
- **未決定事項**: 人間の判断が必要な項目

次のものは、誰の発言由来かにかかわらず本文に書かない。

- 現在のコード構造の説明(確認済みの事実でも)
- 原因の分析や仮説
- 変更するファイルの候補
- 実装方法や実装手順
- 調査の経緯やログ
- 実装時の作業仮説
- 実装者がコードを読んで決められる技術的選択

## タイトル

タイトルにも本文と同じ思想を適用する。実装方法ではなく、何が問題なのか、何を実現したいのかが分かる一文にする。

```text
避ける:
Add GitHubIssueRepository and webhook handler

望ましい:
Portal から作成した GitHub Issue の進捗を確認できるようにする
```

## 長さの扱い

人間が最初から最後まで普通に読める長さに収める。ただし、収めるために要約で意味を潰してはならない。収まらない場合は次の順で対処する。

1. 推論や短寿命な技術情報が混ざっていないか確認して削る
2. 重複した説明を削る
3. 独立した要求や論点なら、issue を分割する
4. それでも判断できない場合だけ、何を残すべきかユーザーに確認する

`<details>` などで詳細を退避することや、「冒頭だけ人間向けで、残りは agent 向けの長大な仕様書」という構成にすることはしない。

## コメントの扱い

このスキルの基準を厳格に適用するのは issue 本文である。コメントには議論や判断の経緯を残す意味があるので、本文と同じ基準では縛らない。ただし、agent が調査ログや実装メモを保存するためだけに長文コメントを追加することはしない。

議論の結果として合意が変わった場合は、必要に応じて issue 本文を更新し、本文がその時点の合意を表す状態を保つ。

## 手順

1. 入力(依頼、会話の文脈、貼り付けられた素材)から記述の候補を抽出する
2. 各候補について、出所と、ユーザーが採用したかを確認し、分類表に従って分類する
3. 分類に応じて、本文への採用、未決定事項への変換、破棄を決める
4. 採用した記述を 5 項目に構成する
5. 全文を読み直し、次を確認する
    - 入力にない要求・制約・設計判断が生えていないか
    - 推測がユーザーの要求・決定に化けていないか
    - 仮説が事実の形で書かれていないか
    - 実装上の技術的選択が未決定事項に混ざっていないか
    - 要約で異なる要求や条件が一つに潰れていないか
    - 人間が全文を普通に読める長さか
6. タイトルを「タイトル」節の基準で付ける
7. ユーザーと対話できる場面では、次のとおり承認を扱って `gh issue create` で作成する。対話できない場面では、手順 5 の確認をもう一周してから作成する

    ```text
    まだ内容をユーザーに見せていない
    → 草案を提示して確認する

    すでに内容をユーザーが確認・承認している
    → 再確認せず作成する
    ```

    ユーザーがすでに issue の内容を確認・承認したうえで作成を依頼している場合、その承認を再度取り直さない。未決定事項が残っていても、それを未決定事項として issue に残すことがユーザーの承認内容と矛盾しないなら、解決や再確認を求めずそのまま作成する。再確認が必要なのは、承認後に要求・制約・スコープなど issue の意味を変更した場合だけとする(このスキルでは agent が勝手に変更しないため、本来起きない)

既存 issue の本文を編集するときも同じ基準を適用する。

## issue-agreement との分担

```text
人間の要求・判断
    ↓
create-issue
    ↓
issue
    ↓
issue-agreement + 現在のコード
    ↓
合意メモ
    ↓
設計・実装
```

- **create-issue**: 人間が決めた要求・意図・制約・未決定事項を、意味を増やさず issue に残す
- **issue-agreement**: 実装開始時に現在のコードを調査し直し、issue との乖離や実装前に必要な判断を確認する
