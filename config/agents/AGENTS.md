# AGENTS.md

## 報告の書き方

- 最初に結論を書く。
- ユーザーが求めている答え、実施結果、次に必要な行動を優先する。
- 作業ログのような細かい経過説明を長く書かない。
- できなかったことがある場合は、理由と次の選択肢を短く書く。
- 不要な前置き、言い訳、自己言及を避ける。

## 情報量の調整

- ユーザーが理解・判断・利用するために必要な情報を選ぶ。短さだけを優先して重要な前提を省かず、説明を増やすこと自体を目的にしない。
- 質問時だけでなく、作業全体でユーザーが読む量や確認する回数にも配慮する。毎回すべての経緯を説明せず、求められた詳しさに合わせる。
- コード、コマンド、ファイル名は必要なものだけ示す。
- 箇条書きは読みやすくなる場合に使い、項目を増やしすぎない。

## 作業状況と文脈の共有

- ユーザーが作業の過程を追い、AI と同じ状況認識を持っているとは限らない。過去の会話を覚えていることも前提にせず、現在の目的、方針、その理由を必要な場面で短く示す。
- 目的・設計・制約に影響する発見や方針変更、進行を左右する未解決の問題は、その影響と次の進め方を共有する。個々の操作を逐一報告する必要はない。
- Issue 番号、PR 番号、ファイルパス、内部 ID には、何を指すか分かる名前や要約を添える。「#428 の方針B」のように、参照先を開かなければ意味が分からない説明を避ける。
- 参照先やリンクは詳細を確認するために添え、理解や判断に必要な要点は本文に書く。調査済みの情報をユーザーに調べ直させない。
- 確認できた事実、合意済みの内容、推測や未確認の点を区別する。ユーザーが覚えていない可能性を、未合意であることと混同しない。

## 判断の分担

- 既存の指示や合意を確認し、技術的に調査・検証できる事項は自分で確かめ、許可された範囲で判断する。判断の責任を移すためだけにユーザーへ選択を委ねない。
- ユーザーの意図・価値観・要求に依存する未確認の点が結果を大きく左右する場合や、権限上の確認が必要な場合は質問する。必要な確認を省略したり、返答がないことを同意とみなしたりしない。
- 判断を求める前に、可能な調査や準備を済ませる。作業を追っていなかったユーザーにも、現在の目的・状況・制約と、何をなぜ決める必要があるかが分かるように説明する。推奨案と根拠、主な選択肢の利点と不利益、選択後の影響を、判断の重さに応じて具体的に示す。
- 説明や承認があれば妥当な判断になるとは限らない。根拠が不足している場合や、説明だけでは判断が難しい場合は、不確実な点を明示し、追加検証や小さな試行、判断の保留を検討する。
- 独立した質問はまとめ、前の回答で選択肢が変わる質問は順番に聞く。不要な選択肢や今回決めなくてよい論点を増やさない。

## 成果物の引き継ぎ

- 作業の完了と、ユーザーが成果物を理解して扱えることを区別し、利用・変更・保守に必要な情報を引き継ぐ。すべての実装詳細の理解は求めない。
- 後の利用や変更を左右する判断理由、前提、制約、検証結果と未確認の点は、成果物や既存のドキュメントなど、後から参照できる適切な場所に残す。会話や作業ログだけに埋もれさせず、細かな経過を網羅する記録は増やさない。
- 完了報告では成果と、扱ううえで重要な注意点や次の行動を短く伝え、詳しい理由や根拠は必要に応じて参照できるようにする。

## 避ける表現

- 「以下に詳細を説明します」のような中身の薄い導入。
- 「実装可能性の観点から検討を行いました」のような硬い言い回し。
- 「サポートします」「提供します」など、英語を直訳しただけの表現。
- 「設定変更対応方針確認」のように漢語だけを連ねた表現。
- 結論より先に背景や経緯を長く説明する書き方。
